# /handoff:write

在会话边界把交接状态写入 `HANDOFF.md`。write 的输入是**本会话上下文综合**——代码扫描（git、测试、TODO）只是代码任务下的辅助手段，日常任务同样适用。

## 适用时机

- **首次**：新任务开始，写一份骨架（只有"任务/为什么"）。
- **收尾**：会话结束前，写全五件事。
- 长时间停滞后恢复，或任务状态重大变化。

会话中途只使用 `/handoff:update`；不要用 write 代替定点更新。

## write 写什么：交接五要素

写给完全没有上下文的新会话看：

1. **在做什么任务**（上下文）
2. **已经完成了什么**（当前进度 → 已完成）
3. **当前卡在哪**（当前进度 → 卡点）
4. **下一步计划**（当前进度 → 下一步）
5. **踩过的坑，绝对不要再踩**（踩坑记录）

模板按此结构：上下文 / 当前进度（已完成 / 进行中 / 卡点 / 下一步）/ 决策记录 / 踩坑记录。

## 默认模式（C 模式，分节决策）

默认 `write` 是分节决策：

| 节 | 处理 |
|---|---|
| 上下文 | 覆盖刷新（当前任务描述） |
| 当前进度 | 覆盖刷新（已完成 / 进行中 / 卡点 / 下一步） |
| 决策记录 | **保留原历史**，新决策追加到顶部 |
| 踩坑记录 | **保留原历史**，新踩坑追加到顶部 |

- 决策/踩坑是历史，write 不得清空或改写；write 无法从代码推导"为什么选 X"，这类理由由用户在会话中 `update` 记录。
- 首次生成：只有"任务/为什么"，进度写"待填充"，决策/踩坑留空。
- 未知信息写"未知"或"无"，不要编造（会话记忆衰减时尤其如此）。

## write full：全量重建

`/handoff:write full` 用于重新构建 `HANDOFF.md`——文档损坏、结构混乱、或需要彻底重来时。

1. **先归档旧内容**：调用归档逻辑，把现有 `HANDOFF.md` 冻结到 `.handoff/`（决策+踩坑；见 archive），确保历史不丢。
2. **重建**：从当前会话上下文与项目状态重新综合全部四节，写一份干净、结构完整的 `HANDOFF.md`。
3. 若旧内容自上次归档以来没有变化，跳过归档，只重建。

## 写作可靠性

- 可从文件系统/工具验证的信息（产出物、代码、文件变更、git）用验证结果。
- 无法验证的（意图、决策理由、卡点叙事）用会话记忆，并在拿不准时标注"不确定"。
- 不编造进度、卡点或决策。

## 幂等与重复执行

- 重复执行 `write`：按 C 模式刷新，决策/踩坑保留，不产生额外归档。
- 重复执行 `write full`：若自上次归档以来 `HANDOFF.md` 无变化，跳过归档、只重建；避免中间态污染历史链。

## 与 update / archive 的边界

| 命令 | 时机 | 行为 |
|---|---|---|
| `write` | 会话边界 | C 模式：状态覆盖 + 历史保留 |
| `write full` | 会话边界（需重建时） | 先归档旧内容，再全量重建 |
| `update` | 会话中途 | 定点补丁：上下文/进度=替换，决策/踩坑=追加 |
| `archive` | 任意时刻 | 只归档快照，不重建 |

如果用户要求在会话中途全量刷新，说明应等到会话边界使用 write；当前只执行安全的 update。
